# 纯终端后端：独立引擎、短信认证与验证边界

2026-10-27，官方 Linux amd64 **10781.21.0.0831**。

## 已经取得的结果

旧交互菜单在短信网关返回动态口令要求后直接回主菜单，见[当时的实测](cli-mfa-proof.md)。这个结论只针对菜单入口。同一个 UniVPNCS 还可以进入 CSDK/RPC 模式，独立编写的 Python 前端通过本地 Unix socket 控制官方引擎，不需要厂商 GUI 或图形栈。

在隔离原型容器内，已经完成一次真实 HiDev 短信流程：

1. 启动官方辅助程序与 UniVPNCS，建立持久的同步请求通道和异步事件通道。
2. 提交一次账号密码，收到短信挑战。
3. 用户提供本次短信验证码；在原引擎、原登录会话内续交一次验证码，没有重新登录。
4. 收到认证成功码 **`0x00020000`**。
5. 显式请求启动 CNEM 隧道，收到 **`0x00070000`**。
6. 通过该 VPN 收到 **4 台内网服务器的真实 SSH banner**。

这些是实际运行结果，不只来自字符串或反汇编线索。全程没有启动 Qt、X11、Xvfb、DBus、VNC/noVNC，没有修改厂商二进制，也没有跳过短信认证或伪造成功码。公开文档不包含真实账号、密码、验证码、网关或服务器地址。

原型阶段的一次 `docker stats --no-stream` 样本为 **14.99 MiB**。单次样本不能代表稳态、峰值或正式镜像的资源消耗，也不包含 Docker Desktop/WSL 的固定平台成本。

## 已实现的正式模块

默认 Compose 的 `native` 构建目标现使用终端前端和官方 CSDK 路径，已经替代旧厂商 CLI 菜单。模块划分为：

- `native_engine`：核对厂商引擎/辅助程序摘要，管理进程和持久通道；异步事件只保留有限数量的消息头元数据。
- `native_rpc` / `native_messages`：有界消息分帧和已验证版本的字段编码。控制头为 24 字节、6 个大端 u32；部分请求体使用小端，不能统一假设字节序。响应 opcode 是结果码，不是请求 opcode 的回显。
- `challenge` / `native_auth`：一次显式登录、一次可能的短信续交，绑定 attempt/challenge ID；总登录期限 600 秒，短信挑战最多 180 秒。失败、超时或取消后要求重启容器，不复用同一引擎的认证上下文。
- `certificate_policy`：默认验证 CA 链和主机名；可选、显式批准的叶证书摘要例外，见下文。
- `native_service` / `native_control`：容器内 root 专用本地控制接口；终端隐藏输入密码和验证码，不将其放入 argv 或配置文件。

已验证的请求顺序如下。请求和响应始终沿用同一原生引擎会话；下表不是公开厂商 SDK 承诺。

| 阶段 | 请求 class/opcode | 预期结果 |
| --- | --- | --- |
| FirstConnect | `1 / 4` | `0x00010000` |
| LinkSelect | `1 / 18` | `0x00010004` |
| 账号密码 | `3 / 5` | `0x0003000a` 要求短信，或 `0x00020000` 已认证 |
| 现有短信挑战续交 | `3 / 17` | `0x00020000` 已认证 |
| CNEM 隧道启动 | `5 / 10` | `0x00070000` |

短信提交前先原子地消费本次挑战；传输结果不确定时也不会自动重发。`AUTH_OK`、隧道启动成功、目标数据面健康是三个独立状态。只有到真实目标的路由、VPN 接口和业务 banner 探针通过，才允许开启网段转发。

当前 **114 项单元测试通过**，包括同引擎短信续交、分帧/EOF/超时、无重复提交、取消与晚到响应、证书策略及状态脱敏。这些测试使用模拟对象。

随后已使用默认 Compose 的正式 `native` 容器完成另一轮真实短信认证。正式状态返回 `authenticated: true`、`tunnel_started: true`、`data_plane_ready: true`；最后一条响应为 class `5`、结果码 `0x00070000`，配置的真实 SSH 业务探针及 **4/4 台服务器的 SSH banner** 均通过。这补充了正式服务模块的实际认证、隧道和数据面证据。

正式容器连接后的单次资源样本为 **18.8 MiB / 384 MiB，CPU 1.26%**。Qt/Xvfb/DBus/AT-SPI/VNC 包检查结果为空；进程只有 tini、Python、官方辅助服务和 UniVPNCS。该样本不包含 Docker Desktop/WSL 固定开销，也不能代表持续负载或峰值。

## 证书策略的边界

没有配置 `approved_certificate_sha256` 时，独立 TLS 预检使用正常 CA 链及主机名验证，登录请求保留引擎证书检查标志。

只有用户独立核验并明确批准当前网关叶证书的 64 位十六进制 SHA256 后，才允许配置这个可选字段。预检不发送 VPN 凭据；只在摘要完全匹配且网关、端口一致时，为本次登录 payload 设置接受证书例外的标志。摘要不符直接失败，不回落到不验证模式，不修改全局配置或系统信任库。

**这是独立 TLS 连接上的预检，不是引擎侧证书 pinning。** 后续官方引擎使用另一条连接，当前没有将其实际叶证书与预检连接绑定的证据。这一连接绑定边界仍然存在，不能据此声称引擎只会接受该 pin。

## 仍需完成的验收

- Windows WireGuard → Docker → 真实 UniVPN 的网段整条链路尚待端到端实测。现有独立 Linux 转发测试不能替代它。
- 分别测量空闲、已连接、业务负载、断网恢复时的资源与行为；原型 14.99 MiB、正式容器 18.8 MiB 的单次样本均不提供持续性能结论。
- 厂商没有为这些观察到的本地接口提供已核实的公开兼容承诺；更换客户端版本或架构必须重新验证，不可略过摘要校验。

早期 [tools/probe_native_rpc.py](../tools/probe_native_rpc.py) 仍只检查启动通知，不负责登录或短信，不能用其输出判断正式后端能力。
